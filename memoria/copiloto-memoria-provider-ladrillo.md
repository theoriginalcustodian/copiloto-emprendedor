**MODELO DE GRAFOS (decisión del operador 2026-07-04 — un tenant = varios grafos):**
- **Grafo general + chat = el user graph** de Graphity. El `user` (= el agente del emprendedor) escribe ahí vía `threads`/`add_messages`; `get_user_context` lo lee cada turno. **Esto es lo único que implementa hoy el MemoryProvider.**
- **Grafos de función futuros (BI, catálogo, …) = group graphs** hermanos (`graph_id` propio, vía `graph.add`), NO el user graph. Hook listo: `MemoryProvider.function_graph_id(cliente_id, fn, namespace=)` fija el naming para que agregar el grafo N+1 sea plug-in sin refactor. Por eso el eje `namespace`/grafo es parámetro desde el día 0.

**Archivos (`apps/copiloto/`):** `graphity_memory_client.py` (cliente HTTP sync thread-memory, httpx inyectable estilo `GoTrueAdmin`; **3er cliente Graphity del repo** — NO confundir con el de la fábrica `deploy/worker/graphity_client.py` async ni el `client_http_plain` generado) · `memory_provider.py` (boundary `recall`/`remember`/`forget`) · `tests/test_memory_provider.py` (19 unitarios MockTransport) · `tests/test_memory_isolation_live.py` (adversarial live).

**Contrato:** `recall(cliente_id, thread_ref)->str` (Context Block por turno) · `remember(cliente_id, thread_ref, messages)->None` (el CALLER batchea ~5-10 turnos + flush; el provider NO tiene estado de sesión) · `forget(cliente_id)` (RTBF).

**Decisiones clave (no obvias):**
- **Aislamiento cross-emprendedor SIN HMAC:** `user_id = f"{namespace}-{cliente_id}"`; el `cliente_id` **ya es UUID v4** (`onboarding.py`/`provision.py` → `gen_random_uuid`) ⇒ no-adivinable por construcción. El server namespacea físico `{tenant}__user_{user_id}` (ADR-040). Aislamiento primario = aplicativo (el thread se ata al cliente_id del request, igual que `context_factory`); UUID = defensa en profundidad. Cero deuda, cero secreto nuevo. [[graphity-aislamiento-cross-tenant-verificado]]
- **Best-effort (degradación elegante):** Graphity caído NUNCA tumba el turno → `recall`→`""`, `remember`/`forget`→no-op logueado.
- **Anti prompt-injection:** el Context Block deriva de contenido del usuario (extraído por LLM) → se envuelve rotulado "datos NO instrucciones" + se neutraliza el delimitador `[/MEMORIA]` (mismo patrón que `memory_activities.format_context` del músculo). [[agente-conversacional-hardening-3-lentes]]
- **Una key global** (tenant Graphity `unreal-copilot`, de `deepseek-worker.env`) para todo el copiloto; la separación entre emprendedores es por user_id, no por key.

**🔥 Warm dirigido por el FRONT (Opción A, commit `d1fd42e`, PR #114, DESPLEGADO+VERIFICADO VIVO 2026-07-04):** el warm del workflow corre 1× al abrir el `ConversationWorkflow`, que se abre CON el 1er mensaje → el 1er turno pagaba el cache-miss. En un copiloto la charla es SIEMPRE la misma (`session_id` persistido en localStorage) → el disparo natural del warm es el **ciclo de vida del front** (abrir la app / entrar a la pestaña de chat), no la llegada de un mensaje. Fix: `POST /warm` (auth per-request, `cliente_id` del token) → `warm_fn(cliente_id)` = `MemoryProvider.warm`; **best-effort: sin memoria (`warm_fn=None`) o fallo de Graphity → `{"warmed": false}`, NUNCA 500** (`def` route → threadpool). El front (`useChat`) lo dispara **fire-and-forget al montar** (entrar al chat / abrir app; Apps→Chat remonta) **+ al volver la pestaña a visible** (`visibilitychange`), con **throttle por sesión (5 min)** — no martillar en remounts (breakpoint mobile/desktop) ni flicks (enfriamiento = LRU, no timer). El warm del workflow queda TAL CUAL (genérico, cubre Telegram); en web pasa a cache-hit rápido. **`build_memory_provider(env)` = fuente ÚNICA de construcción del provider** (gate `GRAPHITY_*`), compartida por `worker_b` (recall/remember) y `serve` (warm) → paga la duplicación, cero drift. Opt-in real (`warm_fn=None` default → apps sin memoria intactas). **Evidencia VPS:** backend 197✓ (+6: /warm 401/ok/noop/never-500 + factory) · frontend 408✓ (+6: mount/visible/throttle/fallo-safe/transporte) + `tsc` limpio · deploy vivo: log `copiloto web warm: ON (Graphity)`, `/warm` sin token→401, **`/warm` E2E tenant real → `200 {"warmed":true}`** contra Graphity vivo. **🐛 Finding CRÍTICO del review adversarial (cazado + fixeado de raíz):** las 3 `execute_activity` de memoria tenían timeout SIN `retry_policy` → reintentos ILIMITADOS (default Temporal) + sin `try/except` → bajo Graphity **LENTO** (no caído: caído fast-failea), un intento >timeout reintentaba infinito → `run()` mudo / loop colgado / ThreadPool agotado (degradación global). Fix: `retry_policy(max_attempts=1)` + `try/except ActivityError` (degrada a no-op) + `MEMORY_TIMEOUT=75s` (worst-case 1 intento) + cliente `max_attempts=1`. **`ConversationWorkflow` era la ÚNICA anomalía sin retry_policy del repo.** Lección: activities best-effort en un workflow durable SIEMPRE con `retry_policy` acotada + try/except.

**🐛🐛 Finding 2 — recall NO funcionaba cross-sesión (cazado por el smoke E2E real, PR #114, commit `e90baf8`, VERIFICADO en vivo):** el `recall` usaba `GET /threads/{id}/context`, que hace RAG sobre los **mensajes DEL THREAD** (`build_context_block` → `_fetch_recent_messages` → `graphiti.search_` con esos mensajes como query). En una **charla NUEVA** el thread no tiene mensajes → sin query → **facts vacíos** → el agente NO recordaba entre sesiones (¡el valor central de la memoria de largo plazo!). El test de aislamiento anterior NO lo detectó porque escribía y leía en el **mismo thread**. **Fix (spike-verificado contra Graphity vivo):** el recall ahora hace `POST /graph/search` sobre el **user graph** con el **mensaje del turno como query** (`client.search_user_facts`, scope=edges) → trae los facts aunque el thread sea nuevo. Separa LECTURA (search, sin efectos) de ESCRITURA (remember/batch, intacto); `call_llm` pasa `payload["user"]` como query; `recall(cliente_id, thread_ref, query)`. **Evidencia en vivo:** charla nueva (thread distinto) → `Martin owns RodadosMartin · lives in Rosario` (antes: VACÍO), prueba borrada con forget. Lección de PROCESO: el smoke E2E DEBE ejercitar la **condición crítica real** (recall en thread distinto al de escritura), no un sustituto (mismo thread) — no codificar la esperanza.
